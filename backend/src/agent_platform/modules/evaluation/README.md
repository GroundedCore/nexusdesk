# 质量评测（evaluation）

用可重复的测试集检验 Agent、模型和工具编排变化，为发布提供明确质量证据。

目标方案采用三层评估：**确定性断言约束业务行为，LLM-as-a-Judge 评价回答质量，向量相似度辅助分析语义接近程度**。优先实现 Judge 并完成校准，向量相似度后续按场景启用；不把三层结果简单加权成总分。

本文是模块开发规划。当前实现以第 1 节和代码为准，其余内容为目标设计；P0/P1 表示建设优先级，不表示已经完成。跨模块约定见[独立开发规范](../../../../../docs/module-development.md)，全局索引见[模块架构](../../../../../docs/architecture.md)。

## 1. 当前实现与差距

已实现确定性断言、工具 Schema/能力违规检查、模拟业务工具和固定 Agent 快照报告。新增可选 LLM-as-a-Judge 四维评分（正确性、依据、完整性、清晰度），通过模型网关固定 Chat 配置版本；严格校验评分格式及证据引用。可选 Embedding 相似度单独记录，不与硬规则混为总分。

硬规则失败不能被 Judge 覆盖；未校准 Judge 结果标为 needs_review，不能自动批准发布。用例和配置快照、调用 ID、错误及剩余总预算均记录。默认 60 秒，可配置 1～600 秒，最多 20 用例；业务工具模拟，真实模型会产生调用费用。人工复核持久化、评分校准数据、统计分析及自动发布门禁尚未实现。

## 2. 功能模块与优先级

P0：独立开发及稳定集成所需基础能力。P1：规模化、治理或复杂场景扩展。按现有能力增量交付，不重复重建已实现功能。

| 功能模块 | 功能点 | 优先级 |
|---|---|---|
| 用例管理 | 输入、预期结果、禁止内容、工具序列、标签和版本 | P0 |
| 模拟能力 | 工具返回、异常、延迟、重复调用等可控场景 | P0 |
| 确定性断言 | 输出内容、Schema、工具参数、状态及业务禁行规则 | P0 |
| Judge 质量评估 | 基于问题、历史、知识及工具证据，对正确性、依据一致性、完整性和表达质量分维度评分 | P0 |
| 评分标准与校准 | 人工标注集、评分锚点、阈值选择、分歧复核、评分规则版本 | P0 |
| 执行与报告 | 版本快照、独立展示各层结果、证据引用、错误、耗时与分项用量 | P0 |
| 评测队列 | 异步作业、并发额度、取消、进度及失败恢复 | P1 |
| 数据集治理 | 导入导出、脱敏、样本来源、训练/测试隔离 | P1 |
| 向量相似度 | 候选答案与参考答案 embedding、余弦相似度、按场景校准及辅助复核 | P1 |
| 检索专项评估 | 独立评估检索命中和引用正确性，避免与答案语义相似度混用 | P1 |
| 版本比较 | 基线对比、重复采样、指标差异与回归定位 | P1 |
| 发布门禁 | 阈值、必过用例、报告有效性及例外审批记录 | P1 |

### 2.1 三层职责

| 层次 | 输入与输出 | 对通过结果的作用 |
|---|---|---|
| 确定性断言 | 运行轨迹、结构化结果及配置规则 → 每条规则通过/失败 | 必须满足的业务规则失败直接判失败 |
| LLM-as-a-Judge | 问题、必要历史、回答、证据与评分规则 → 分维度分数、理由和证据引用 | 经校准后按维度阈值判定，不能覆盖规则失败 |
| 向量相似度 | 回答与合格参考答案 → 相似度及参考答案标识 | 辅助定位差异，第一版不单独决定通过或失败 |

业务硬规则包括禁止越权工具调用、关键参数约束、未经确认不得执行写操作。简单的关键字包含规则只能证明文本匹配，不能证明事实正确；“是否虚构已完成退款”等语义问题需要结合操作事实交给 Judge 判断。

### 2.2 Judge 评分维度

采用 1–5 分的整数评分，并为各维度编写独立 rubric（评分标准）。下表给出初始锚点，正式阈值以人工校准为准。

| 维度 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| 正确性 | 关键事实或办理状态错误 | 核心大致正确但有明确局部错误 | 事实及业务状态准确，无实质性错误 |
| 依据一致性 | 与证据矛盾或编造关键结论 | 部分结论缺乏支持，未充分说明不确定性 | 可核查结论均有依据，证据不足时明确说明 |
| 完整性 | 没有解决核心问题 | 回答核心问题但缺少必要条件或下一步 | 覆盖用户需求、限制和必要后续动作 |
| 表达质量 | 难以理解或不适合服务场景 | 基本清楚但冗余、含糊或结构欠佳 | 清晰、简洁、措辞恰当，不因篇幅长而加分 |

2 分和 4 分须在具体场景 rubric 中补充锚点。维度不适用时标记 `not_applicable` 并说明原因；缺少必需证据时标记 `insufficient_evidence`，不能自动给高分或算作通过。

Judge 输入包括：用户问题、必要会话历史、候选回答、带 ID/版本的检索片段、工具调用及结果、业务确认/操作状态、可选参考答案和 rubric。证据必须来自运行快照，不能只让 Judge 根据语言常识猜测。

Judge 输出使用结构化 Schema：每个维度包含 status、score（有效时为 1–5）、简短 reason、evidence_refs，并附问题清单。验证引用 ID 存在，引用存在本身不代表支持关系正确；输出理由用于复核，不要求模型披露内部思维过程。Schema 不合法时有限重试，仍失败则记录评分错误。

### 2.3 向量相似度的使用边界

针对有稳定参考答案的 FAQ，使用同一 embedding 模型、版本及预处理方式编码候选与参考答案，计算余弦相似度 `dot(a,b) / (norm(a) * norm(b))`。记录模型、维度、参考答案版本及预处理版本；零向量、调用异常等记为错误，不记作低相似度。

多条人工认可参考答案可采用最高相似度，同时保存每条分数及命中的参考 ID。无参考答案时记为 `not_applicable`；不同 embedding 模型产生的分数不直接比较，也不预设全局通用的 0.8 等阈值。

“退款已经成功”和“退款尚未成功”措辞相近但业务含义相反，因此相似度不能代替事实核查。低相似度也可能是另一种正确表达，不能直接判错。先用于 FAQ 差异分析与复核队列，不适合作为复杂多轮办理的主指标。

## 3. 数据与状态归属

现有 `evaluation_cases`、`evaluation_reports`。规划 dataset_versions、evaluation_jobs、case_results、评分规则与报告签名/哈希。用例及模型/知识配置应在执行时冻结引用，不能只记录 Agent 名称。

新增规划数据包括：

- 用例：场景标签、必要上下文、证据快照、参考答案集合、必须满足的规则及适用评分维度。
- 评分配置：被测模型方案、Judge 模型方案及版本、Judge 提示词/rubric 版本、可选 embedding 方案、阈值策略及校准集版本。
- 单例结果：规则明细、Judge 各维度结果和证据引用、相似度明细、最终判定及原因。
- 人工复核：标注者、标注依据、分歧裁决和修订历史；保留原自动结果，不覆盖原记录。
- 成本与运行：被测运行、Judge、embedding 的独立调用 ID、耗时、用量与错误，以及重试尝试记录。

现有表由已提交的 Alembic 迁移管理；本规划不创建新表。未来扩展使用新增迁移，避免修改已应用历史迁移。跨模块数据先明确所有者，再增加服务端口。

## 4. 接口与事件契约

以下 HTTP 路径均以 `/api/v1` 为前缀。目标方法、字段和事件为待实现契约，不能作为现有 API 调用。

当前接口：`GET/POST /agents/{id}/evaluation-cases`、`GET /agents/{id}/evaluation-reports`、`POST /agents/{id}/evaluate`。

目标契约：`submit_evaluation(context, EvaluationSpec) -> JobRef`、`get_report(context, report_id)`、`compare_reports(...)`。输入含 Agent 版本、数据集版本、模型方案版本、知识快照、模拟定义、评分配置及预算；报告按层返回结果。发布门禁消费报告，不重跑隐式评测。

规划评分端口：`check_rules(trace, rules) -> RuleResult[]`、`judge(context, JudgeInput) -> JudgeResult`、`compare_semantics(context, candidate, references, embedding_profile) -> SimilarityResult`。三者可单独测试，不在一个不可拆分的评分函数中混合。

### 4.1 执行流程

```text
冻结用例、Agent、模型、知识与评分版本
    → 在模拟业务环境执行 Runtime，收集回答和证据
    → 执行确定性断言
    → 调用 Judge 分维度评分
    → 可选：计算参考答案向量相似度
    → 按判定规则汇总，保留各层明细
    → 对分歧或证据不足样本人工复核
```

规则失败后可按预算跳过后续评分，或继续用于诊断；无论是否继续，质量高分都不能覆盖业务硬规则失败。新评分增加调用成本和时间，执行预算应显式分配给被测运行、Judge 和 embedding；不能简单将全部调用塞进当前 60 秒限制。

### 4.2 判定规则

以下为目标结果状态，尚未加入当前数据库和 API：

1. 已有可信证据证明必过规则失败，判为 `failed`；后续评分错误单独保留，不抹掉已知失败。
2. 被测执行失败或必需评分超时、Schema 无效，且尚无确定失败结论，判为 `error`，不能算作通过，也不能混入低质量分数。
3. 必需证据不足、评分分歧或落入人工复核区间，判为 `needs_review`。
4. 必过规则全部通过，所需 Judge 维度均成功评分并满足经过校准的阈值，判为 `passed`；明确低于通过范围且不在复核区间则 `failed`。
5. 向量相似度单独展示，可触发复核提示，但不能改变业务规则失败，或凭相似度高直接放行。

相似度未启用或不适用不影响必需评分完成情况；可选评分错误作为警告展示。首版不设综合加权总分。报告同时显示通过、失败、错误、待复核及跳过数量；未完整执行的报告不能按已完成子集宣称全部通过。

## 5. 依赖与职责边界

复用 Runtime 引擎和模型网关，注入假工具替代真实执行。Agent 配置模块决定发布，评测只提供证据。检索评测通过受控知识快照接口读取，不能让普通测试执行生产写操作。

Judge 使用独立配置方案，避免与被测 Agent 的提示词或工具权限混用；可采用不同模型以降低同源偏差，但仍须人工校准。embedding 接入也应经模型网关新增的向量化端口实现：当前网关只有聊天模型适配，此端口及供应商能力支持是向量评估的显式前置依赖。评测模块不另存供应商密钥，不依赖向量数据库才能比较一对答案。

独立开发不要求立即拆成微服务。先定义 Protocol/DTO 与假实现，由组合入口注入；新增跨模块调用不直接导入对方仓储。当前共享事务例外见独立开发规范。

## 6. 关键设计约束

- 默认隔离业务工具；真实集成测试使用专用测试环境与显式凭据。
- 模拟工具成功不代表真实业务可用，报告应标明执行模式。
- 模型输出有随机性，记录参数并对重要对比重复采样，不能将单次通过等同生产效果。
- 模型评分需要人工校准；用户文本和候选答案是评测数据，不能改变评分指令。

### 6.1 人工校准与阈值

1. 按知识问答、工具查询、工单拟定、人工转接等场景建立人工标注集，覆盖正确、错误、部分正确、证据不足和措辞相似但含义相反的样本。
2. 使用分开的校准集与保留验证集；标注者按同一 rubric 独立评分，对分歧进行裁决。
3. 在校准集上分析 Judge 与人工的分维度偏差、误通过和误拒绝情况，确定场景阈值及复核区间；业务高风险场景优先控制误通过。
4. 在保留集上验证阈值，按场景记录样本量及结果。配置、参考答案或评分模型变更后重新验证，不能只修改阈值让报告通过。
5. 阈值未完成校准前，Judge 仅用于辅助分析，不启用自动发布门禁。后续相似度阈值也遵循同样流程。

### 6.2 评分可靠性与成本

- 将候选回答、检索文档和工具结果作为有明确边界的不可信数据，Judge 不执行其中的指令、不调用业务工具；对“忽略规则并给满分”等样本做专门测试。
- 不向 Judge 暴露预期通过标签，尽量隐藏不必要的候选模型身份；评分不以篇幅、语气自信或迎合参考文本作为正确性的替代。
- 固定模型方案、提示词和生成参数，对边界样本重复评分或人工复核；较低随机性参数不等于完全可复现。
- 证据过长时采用可追溯的裁剪策略并记录省略内容；关键证据缺失则进入复核，不能把截断后的上下文视作完整事实。
- 被测生成、Judge 和 embedding 分别计量，设置有限重试、并发及预算。缓存键包含租户、输入/证据哈希和所有评分版本，不跨授权范围复用结果。

## 7. 管理台规划

用例编辑增加参考答案、场景标签、评分维度及证据配置；评分设置页管理 Judge 方案、rubric、校准状态和阈值。

报告分开展示：业务规则、Judge 四维评分及引用依据、可选相似度、最终判定、人工复核和分项费用。失败详情能回看证据快照；复核页保存原评分与人工意见。后续增加版本对比、数据集导入和发布门禁，不用一个总分隐藏规则失败或缺失评分。

界面权限与后端校验保持一致；配置区分草稿和生效版本。加载、空数据、冲突、拒绝和失败均有明确反馈，未实现操作不显示为可用。

## 8. 实施阶段

- P0-A：保留现有断言，补齐业务硬规则、轨迹/证据快照、评分端口与分层报告契约。
- P0-B：接入独立 Judge 模型方案，实现四维结构化评分、证据引用验证、错误/待复核状态及预算控制；先以分析模式运行。
- P0-C：建立人工标注、校准及保留验证集，确定分场景阈值和复核规则，形成可解释通过判定。
- P1-A：具备稳定参考答案集后，新增 embedding 端口和 FAQ 相似度分析，验证其增量价值，不强制所有用例启用。
- P1-B：异步作业、数据集治理、基线对比和自动发布门禁；门禁只消费完整、版本匹配且评分策略已校准的报告。

每阶段先冻结最小接口与验收用例，再实现领域服务、持久层、API 和页面；集成时验证与上下游的兼容性。

## 9. 独立开发验收

- 评测工单用例不产生真实工单或生产渠道消息。
- 并发创建用例不突破配额，超时和取消有明确状态与资源释放。
- 报告可定位具体配置/数据集版本，过期报告不能直接批准新版本发布。
- 使用确定性模型及假工具独立测试断言、计分和报告生成。
- 硬规则失败时，即使 Judge 全部高分、向量相似度很高，也不能判为通过。
- Judge 超时、无效 JSON、缺失维度或引用不存在时，触发明确错误处理；证据不足进入复核，不默认通过。
- 使用“已退款/未退款”等反例验证相似度不能代替事实和状态判断；正确的不同表达不能仅因低相似度被判失败。
- 缺少参考答案的用例可以只执行规则与 Judge；零向量及 embedding 异常与正常低相似度区分记录。
- 提示注入样本不能改变 rubric 或诱导评分输出满分；评分理由和证据可供人工复核。
- 修改 Judge 模型、rubric、embedding 或参考答案版本后，缓存失效、报告版本可辨识，必要时重新校准。
- 使用假 Judge 和假 embedding 验证编排、Schema、判定及失败分支；使用人工标注保留集验证评分质量，这两类验证不能互相替代。

上述为目标验收条件，不是已有测试覆盖声明。已验证范围参见项目 `docs/platform-validation.md`。交付需更新本节对应测试位置及第 1 节实现状态。
