# 知识服务（knowledge）

建设企业级文档智能解析与知识加工能力：参考 Foil 的异步分页解析架构，将 PDF、Office、图片等非结构化资料转换为结构化 JSON/Markdown，再构建可授权检索、可引用、可追溯的知识索引。

面向知识库构建、RAG 数据加工、智能搜索和合同审核的数据准备场景。合同风险识别与审批属于上层业务应用，本模块负责还原文档、提供证据及检索能力，不直接承诺合同审核结论。

本文是模块开发规划。当前实现以第 1 节和代码为准，其余内容为目标设计；P0/P1 表示建设优先级，不表示已经完成。跨模块约定见[独立开发规范](../../../../../docs/module-development.md)，全局索引见[模块架构](../../../../../docs/architecture.md)。

## 1. 当前实现与差距（2026-09-22）

文档中心、目录、批量上传、人工/自动流程、文档跨知识库关联、分片草稿、逐库发布版本和统一检索已落地。操作说明及验收见 [知识库工作台实施说明](../../../../../docs/knowledge-workspace.md)。本节描述代码现状，后文仍保留长期规划。

- 本地解析 TXT、Markdown、数字 PDF、DOCX、PPTX、XLSX、CSV；扫描 PDF、图片及旧格式仍需外部 HTTP Parser，未配置时明确报错，不宣称全格式已验收。
- 分片支持结构、固定长度、递归、分隔符、按页、表格行组、FAQ、受长度约束的整篇；表格支持工作表、表头行和问答列选择。提供参数预览、人工编辑、合并、拆分、启停与草稿版本冲突检查。
- 独立 PostgreSQL 队列执行解析和索引任务，支持租约心跳、任务取消/重试、丢失 Worker 恢复、同租户文件内容去重。自动导入在事务内登记后续发布请求。
- PostgreSQL 存储文档和版本；MinIO/S3 归档原件，当前仍保留 PG 原件以支持下载和重试。Milvus 按构建创建独立集合，成功后原子切换发布版本；失败保留旧索引与旧检索内容。旧集合延迟清理，失败清理记录可重试。
- Agent 与测试页面共用关键词/向量/混合检索，使用排名融合、可选 Rerank、去重及上下文字符预算。Embedding/Rerank 绑定模型网关固定发布版本。召回后按租户、文档启停和知识库发布版本再次过滤。
- 已完成真实 PostgreSQL、MinIO、Milvus 链路测试；模型测试使用 demo 适配器，不能代表真实语义质量。尚未接入外部 OCR/Parser。

现阶段限制：默认单文件 20 MB、提取文本默认 200 万字符（AGENT_KNOWLEDGE_EXTRACTED_CHARS 可配置）、单文档 10000 分片、单次索引 10000 分片；分片按字符而非 Token 计量。父子分片、音视频、知识图谱和特殊格式完整验收属于后续范围。DOCX 引用使用内容块/标题而非推测物理页码。没有为了显示进度而虚构百分比。

### 2.1 多格式文档接入

目标覆盖范围如下。格式支持以部署中已注册的转换器及兼容性样例验收为准，不能仅凭扩展名宣称支持。

| 格式 | 处理策略 | 阶段 |
|---|---|---|
| TXT、Markdown | 保留现有直接文本入口，记录来源位置 | 已有能力，逐步接入新版本体系 |
| PDF | 校验密码/完整性，获取页信息；区分数字文本与扫描页面 | P0 |
| PNG、JPG、JPEG | 保留原图，生成标准页面及 PDF 派生件 | P0 |
| Word、DOCX/DOC | 转换 PDF，保留原生段落、表格等可获取信息 | P0 选定转换器后验收 |
| PPT、PPTX | 转换 PDF，保留幻灯片编号及可提取备注 | P0 选定转换器后验收 |
| RTF、ODT | 对应文档转换适配器 | P0 格式验收 |
| Excel、XLS/XLSX | 原生提取工作表、单元格、公式及合并关系；PDF 用于视觉派生预览 | P0 格式验收 |
| OFD、CAJ、XPS | 独立转换适配器，验证许可、字体、平台依赖及版式保真度 | P0 格式验收 |

格式适配器配置包含实际支持的子格式、转换器/Parser 版本、依赖及许可要求、测试样例和可用状态。逐项集成不等于缩减目标范围；任一目标格式尚未通过验收时，必须显示未就绪，不得宣称完整格式支持。

Excel 不以 PDF 作为唯一事实源，避免分页造成单元格和公式信息丢失；其他格式也保留原始文件和原生定位信息。加密、损坏、格式不支持或超限文件返回具体错误，不无限重试。

### 2.2 预处理与大文档处理

以文档为调度单位，页面或小批只是任务内部进度单位，不创建 parent/child 队列。100 页 PDF 对应一个文档任务，Worker 可按小批读取和保存结果，不要求单次模型请求处理整个文档。

按格式和页面质量选择处理路径：

- TXT/Markdown 直接处理文本及结构。
- 数字 PDF 优先提取可靠原生文本；扫描页走 OCR，复杂版面按 Parser 能力走视觉解析；混合文档允许逐页选择。
- Word/RTF/ODT/PPT 等使用对应转换器，必要时产生标准 PDF；保留原生段落、幻灯片和备注信息。
- Excel 保留原生工作表、单元格、公式和值；PDF 仅作可选预览。
- 图片及 OFD/CAJ/XPS 经相应适配器转换后进入统一解析端口。

视觉路径记录页数、尺寸、方向、DPI、转换器版本及原始位置映射。原文、标准 PDF、页面图、裁剪图和导出文件存入 MinIO/S3，数据库保存对象引用与校验信息。文件转换只由适配器负责一次，不在 Backend 和 Parser 重复做同一转换。

支持页级输出的 Parser 每页/批次完成就保存；仅提供整文档结果的服务先保存结果对象，再流式导入，限制内存使用。仅在适配器明确支持且验证结果一致时从检查点续跑，否则整文档重试；不能根据“已保存第 10 页”假定所有 Parser 都能从第 11 页继续。

### 2.3 PostgreSQL 单任务队列

新增知识任务表，与客服 Runtime 的队列、并发和 Worker 进程分开。任务记录包含 job_id、tenant_id、document_version、task_type、state、stage、attempt、owner、lease_until、next_run_at、deadline、cancel_requested、checkpoint_ref 和 error。

首版按就绪时间及创建时间领取，不建设高低优先级双队列。Worker 在短事务中通过行锁及 SKIP LOCKED 选择任务、更新 owner/租约并递增 attempt；提交事务后才进行转换、网络及模型调用。PostgreSQL 是执行所有权与重试次数的唯一权威来源，不引入 Redis 租约。

- 任务创建和业务记录同事务提交，数据库本身即队列，无需为入队额外建设 Redis 派发器。
- 一个文档任务按阶段完成转换、解析和结果保存；同一队列可用 task_type 区分文档处理与索引构建，采用同一 Worker 类型，不增加第二套调度体系。
- 独立心跳协程续租；页级提交及终态转换校验 owner、attempt、租约和取消标志，事务保持短小。
- 暂时失败按有限次数与 next_run_at 退避；损坏、格式不支持或参数错误直接失败。租约过期后重新领取仍增加 attempt，旧 Worker 无权提交。
- 文档导入使用幂等键；同一版本的重复构建受唯一键/活跃任务约束，重复提交返回原任务。
- 取消排队任务可直接终止；执行中先设置取消标志，停止继续处理，最终终止由 Worker/过期回收确认。取消请求被受理不等于远端 GPU 已停止。

配置 Worker 数量、每进程并发及超时，初期单进程小并发部署。扩展进程时总上限按进程数计算并校验 Parser 容量，不把进程内 semaphore 当成集群全局限额。文件上传与数据库提交仍需孤儿对象回收；Milvus 外部写入保留后文的持久构建清单/outbox，不能误当成解析队列。

### 2.4 统一 Parser 适配器

Backend 只调用统一文档解析端口，根据文件类型选择适配器，不直接选择 Layout/General GPU 实例。首版配置服务地址、凭据引用、能力、超时及并发即可；服务发现、GPU 资源分配和模型内部批处理由所接入的解析服务自行管理。

适配器能力至少声明 supported_formats、output_schema_version、supports_progress、supports_resume、supports_cancel 和 max_input_limits。缺少某项能力时返回明确限制，不向前端展示不可兑现的续跑或立即取消操作。

Foil 可以作为一种后端适配器，其内部可以使用 Layout→General、MU2.5-VLM、PaddleOCR-VL 或其他模型。所选模型标识、权重、许可、推理后端兼容性及质量需在接入时验证；这些不是知识库自建两套 Worker 池的前置要求。其他转换器/Parser 可以组合实现完整格式覆盖，不要求一个模型承担所有格式。

如后续实际出现大文档排队、单任务吞吐不足或多 GPU 调度需求，再依据指标引入页任务并行或 Redis 队列。当前契约预留扩展能力，本版不实现这些调度组件。

### 2.5 结果标准化与知识加工

```text
DocumentVersion
  └─ ParseRevision
      └─ Page
          └─ ParseChunk
              ├─ Text
              ├─ Title
              ├─ Table
              ├─ Formula
              └─ Image
```

标准化处理包括页码偏移修正、坐标换算、元素类型映射、阅读顺序、页眉/页脚/页码标记、HTML/Markdown 表格、LaTeX 公式、图片裁剪及对象存储。原始识别结果和警告保留，页眉页脚优先标记而非不可逆删除；合同条款等重要内容不能因过滤规则丢失。

**解析 Chunk 与检索 Chunk 分离**：ParseChunk 保留页面布局与证据，RetrievalChunk 按标题、段落、表格语义及 Token 预算组合或切分，记录 source_chunk_ids 和定位映射。embedding、关键词索引和重排基于检索 Chunk；修改检索切分无需重新 OCR。

每个成功页面/批次独立落库，不在内存等待全篇完成。先按 `(tenant_id, doc_id, document_version, parse_revision)` 确定结果集合，再按 `page_num + seq` 稳定排序；对外支持分页 JSON、流式生成 Markdown、附件引用和失败页信息。

跨页表格、跨页段落在聚合阶段通过显式关联处理，保留原页元素和来源。部分成功结果可以预览，但默认不发布为在线知识版本；全部必需页、结果校验及索引完成后原子切换当前生效索引。

### 2.6 分片策略全景

统一管理三个层次，不能将其混用：文档任务内部的页范围批次控制处理内存与进度；ParseChunk 是版面证据元素；RetrievalChunk 是检索与生成单元。10 页处理批次不意味着一个独立队列任务，也不意味着合成一个向量。

策略目录全部纳入规划，按阶段实现并标识可用状态，不要求第一版同时上线所有算法。

| 策略 | 方法 | 优点与适用场景 | 限制 | 计划 |
|---|---|---|---|---|
| 固定长度 fixed | 按字符或 Token 窗口切分，支持重叠 | 成本低、易复现，作为效果基线和最后兜底 | 容易切断句子及结构；必须区分计数单位 | P0 基线 |
| 递归 recursive | 按段落、句子、词/Token 等分隔层次逐步细切 | 通用纯文本，尽量保留自然边界 | 不自动理解章节含义；中文须配置标点和边界 | P0 |
| 句段 sentence_paragraph | 先识别完整句子/段落，再组合到预算内 | FAQ、说明文字、短知识条目 | 短片缺背景，长段需要继续拆分 | P0 混合策略内部规则，P1 独立配置 |
| 结构 structure | 按标题层级、章节、条款、Markdown/HTML 结构组织 | 制度、合同、手册，保留主题及层次 | 依赖结构识别质量，需处理误识别标题 | P0 混合策略内部规则，P1 独立配置 |
| 按页 page | 页面作为不可跨越边界，超长时页内继续细切 | PPT、表单、独立页面内容及精确定位 | 可能拆断跨页段落/表格，不作为所有 PDF 的默认方案 | P0 PPT 默认规则，P1 独立配置 |
| 语义 semantic | 对相邻句段编码，根据相似度变化确定边界 | 标题少、主题变化明显的长文本 | 增加 embedding 成本；阈值依赖模型和语料，不保证优于结构切分 | P1 |
| 混合 hybrid | 先按结构分组，再按 Token 上限拆分并合并兼容的小片 | 企业复杂文档默认方向，兼顾结构与长度 | 需定义合并范围及不同元素规则；这里的 hybrid 指结构＋长度约束 | P0 默认 |

所有策略须输出来源映射及稳定顺序。原始文本存在数字、日期、否定词或例外条件时，不能为了达到目标长度丢弃这些内容。

### 2.7 上下文增强策略

这些能力分别作用于切分、索引或检索阶段，不应全部塞进一个 splitter，也不是互斥的七种基础算法之外的同类选项。

| 策略 | 生效阶段与方法 | 使用约束 | 计划 |
|---|---|---|---|
| 重叠窗口 overlap | 切分时为相邻片段保留重复内容 | 优先按句子重叠，控制索引膨胀；不跨权限或无关章节补齐长度 | P0 |
| 父子分片 parent_child | 小片建立检索索引，命中后按需返回父章节/较大内容单元 | 保存 parent_id，父内容仍受授权、版本及总上下文预算限制；合并重复父节点 | P0 保留关系，P1 扩展检索 |
| 句子窗口 sentence_window | 对单句建索引，命中后扩展前后若干句 | 保存句子邻接关系；扩展不跨未授权范围，最终去重并限长 | P1 |
| 上下文补充 contextual | 为索引内容附加标题路径或与该片相关的文档背景 | 标题路径可直接提取；LLM 生成背景需校验、单独存储，不能当原文引用 | P0 标题路径，P1 生成背景 |
| Late Chunking | 对模型窗口内较长文本先计算上下文 Token 表示，再按片段范围聚合向量 | 不是先生成整篇单向量再切；须有 Token 表示/分片池化能力或支持此功能的服务 | P1 实验 |

Late Chunking 的边界仍可由结构或其他策略给出，改变的是向量编码与聚合流程。超过 embedding 上下文窗口的文档仍需分组编码，不能承诺跨整篇任意长度保留上下文；当前普通 embedding API 是否支持此能力必须单独验证。

父子返回和句子窗口可以与结构切分组合，但应有明确优先级、去重及扩展预算，不能叠加后无限扩大上下文。首版保存父章节关系，P1 启用扩展检索时优先验证父章节补充；只有业务用例证明需要时再启用句子窗口或生成背景。

### 2.8 默认组合及按内容处理

本项目第一阶段默认采用 **结构优先＋Token 限长＋按元素处理＋完整来源映射**，保留父关系以便后续扩展检索；无可靠结构时回退到递归切分。纯固定长度保留为基线和末级兜底。语义切分及高级增强先作为可对照实验，不直接替换全部文档。

```text
ParseChunk（原页元素和证据）
    → 修复阅读顺序和已确认的跨页连续关系
    → 标题/条款/表格等结构单元
    → 按元素规则组合，使用 Token 预算限长
    → RetrievalChunk ＋ 父结构/相邻关系 ＋ 来源映射
    → 小片检索
    → 按需扩展父结构或窗口，重新校验权限、去重、限长
```

| 内容类型 | 默认处理规则 |
|---|---|
| 正文 | 同一标题范围内按段落组合；过长段落按句子递归切分；短片仅在结构和权限兼容时合并 |
| 合同/制度 | 保留条款编号、标题路径及条件/例外关系；超长条款拆为子片但保留完整父条款引用 |
| 表格 | 小表整体保留；大表按完整行组切分并重复必要表头，保留表 ID、行列定位、单位及脚注关联 |
| 超宽或单行超长表格 | 使用显式列组/单元格子片及主键关联，无法安全切分时记录警告；不能静默截断 |
| PPT | 默认单幻灯片范围，关联标题、正文、图注及可用备注；超长页面仍需细切 |
| Excel | 按工作表及逻辑表区域组织，再按行组切分；保留列名、单元格地址、公式与值的来源 |
| 图片/公式 | 关联图注、编号和必要解释；保留对象/原页引用，生成描述与原始内容区分存储 |
| 扫描或无标题文档 | 先修复布局阅读顺序，使用句段/递归切分；主题切分可作为后续对照 |

跨页不必然是语义边界。正文只有在连续关系可靠时合并；表格合并需核对列结构、标题和续表关系，不能单凭相邻页号合并。所有 Token 预算包含标题路径、重复表头及其他实际送入 embedding 的附加内容。

### 2.9 可版本化配置与策略端口

规划 `ChunkingProfile`，发布后固定版本，Agent 或知识库引用已发布配置。以下字段是目标设计，不是现有可调用 API：

| 配置组 | 主要字段与规则 |
|---|---|
| 基础策略 | strategy、strategy_version、fallback_strategy、length_unit |
| 长度预算 | target_tokens、max_tokens、min_tokens；满足 min ≤ target ≤ max，最终文本不超模型预算 |
| Tokenizer | tokenizer_id/version，与索引 embedding 模型兼容；字符数不能冒充 Token 数 |
| 结构规则 | heading_levels、keep_title_path、merge_small_sections、allow_cross_page、元素类型策略 |
| 重叠 | overlap_mode、overlap_tokens/sentences；必须小于有效窗口并保证切分前进 |
| 表格 | repeat_header、row_group_budget、oversize_policy，连同表头一起计数 |
| 语义 | embedding_profile/version、句段缓冲、阈值方法及阈值；记录校准集 |
| 检索扩展 | parent_return_mode、window_before/after、max_expansion_tokens、去重策略 |
| 生成背景 | contextualizer_profile/version、提示词版本、长度、校验与失败处理 |
| Late Chunking | 编码方案/版本、上下文窗口、聚合方法及跨度到 Token 的映射 |

具体默认数值在目标 tokenizer 与代表性语料上确定；方案不把某个固定 Token 数或重叠比例当成通用最优值。配置应可保存预览结果，发布时检查能力兼容、超长处理及索引成本上限。

规划端口：

- `Chunker.chunk(parsed_document, profile) -> RetrievalChunk[]`：处理边界与来源，不调用真实业务工具。
- `ChunkEnricher.enrich(chunks, context, profile)`：附加标题或生成背景，保留原文与派生文本区分。
- `EmbeddingEncoder.encode(chunks, profile)`：普通逐片编码或受支持的 Late Chunking，不改变原文事实。
- `ContextExpander.expand(hits, scope, budget)`：父子/句子窗口扩展、版本及权限复查、去重和限长。

配置、算法、tokenizer、背景模型或 embedding 版本变化时生成新的 index_version；原 ParseChunk 可复用，不能为调整检索分片强制重新 OCR。分片 ID 在同一构建版本内稳定，重建不混用不同版本的父子关系或缓存。

## 3. 数据与状态归属

现有 `knowledge_bases`、`knowledge_documents`、`knowledge_versions`、`knowledge_chunks` 保持兼容；当前 knowledge_chunks 是文本检索片段，不直接重定义为布局元素。

| 规划实体 | 主要字段与职责 |
|---|---|
| 文档版本/文件清单 | tenant、kb、原文对象、内容哈希、MIME、大小、转换版本 |
| 文档任务 | job_id、task_type、文档版本、阶段、状态、attempt、owner、lease、next_run_at、取消标志及错误 |
| 页面进度/检查点 | job_id、页面或批次、结果对象、有效性校验及 Parser 恢复句柄；不是独立队列任务 |
| 页面 | 文档/解析版本、page_num、尺寸、旋转、图像对象及转换映射 |
| ParseChunk | chunk_id、page_num、seq、type、bbox、内容、来源区域及识别质量信息 |
| 解析产物 | 标准 PDF、JSON、Markdown、裁剪图、校验和、schema_version |
| RetrievalChunk/索引版本 | 内容、source_chunk_ids、切分配置、embedding 模型版本及索引状态 |
| 分片配置版本 | 策略、tokenizer、预算、元素规则、增强组合及配置哈希 |
| 检索结构关系 | parent_id、prev/next、标题路径、字符/Token 来源跨度及权限范围 |
| 增强产物 | 原文与索引文本分别保存，背景生成版本/证据、Late Chunking 编码范围及缓存键 |
| 外部写入清单/outbox | Milvus 等外部索引写入意图、批次校验及重试；不用于 PostgreSQL 队列入队 |

三类版本独立：document_version 对应原文变更；parse_revision 对应解析模型/配置与纠错结果；index_version 对应检索切分和 embedding。产物及引用必须携带版本，不能把模型重解析覆盖成原文新版本。

解析页码统一为 1 起始；seq 定义为页内 0 起始且在一个解析版本中稳定。bbox 采用 `[x0,y0,x1,y1]`、左上原点、按纠正旋转后的页面归一化到 `[0,1]`，同时保存原始尺寸与变换关系。文本入口使用独立的行号/偏移 locator，不伪造 PDF 页码。表格保留结构及渲染文本，公式保留 LaTeX，图片只保存受控对象引用；识别置信值如存在，需注明来源，不能跨模型直接比较。

规划任务状态为 queued/running/succeeded/failed/cancelled，取消申请用 cancel_requested 字段表达，有限重试重新进入 queued。running 携带 converting/parsing/normalizing/indexing/validating 等阶段。部分页失败保留结果和失败页清单，但任务终态为 failed，不新增父子任务状态机。解析成功与索引可发布仍分离；页数未获取时只展示当前阶段，进度从已持久化的完成页集合核对，不能靠重复回执递增。

现有表由已提交的 Alembic 迁移管理；本规划不创建新表。未来扩展使用新增迁移，避免修改已应用历史迁移。跨模块数据先明确所有者，再增加服务端口。

### 3.1 分层存储设计

| 存储 | 保存内容 | 定位 |
|---|---|---|
| PostgreSQL | 知识库、权限、文档/解析/索引版本、任务、Page、ParseChunk、RetrievalChunk 正文与来源、发布清单和 outbox | 权威业务事实与索引重建依据，同时保留关键词检索 |
| Milvus | RetrievalChunk 的向量、稳定关联 ID、版本和用于过滤的必要标量字段 | 可重建的向量检索投影，不独立决定授权及在线版本 |
| MinIO/S3 | 原文、PDF、页面图、裁剪图、JSON/Markdown 导出；可选 embedding 构建产物 | 大文件及派生产物，按权限访问 |
| Redis（可选，非本版依赖） | 后续有证据需要时用于缓存或调度扩展 | 当前解析队列与租约全部在 PostgreSQL |

Milvus 内部可能使用对象存储等组件，其部署依赖按所选版本配置；与业务文件使用独立 bucket/前缀和权限，不将 Milvus 内部文件当作业务附件管理。

### 3.2 Milvus Collection 与字段

初期按 **embedding 空间/模型版本＋向量维度＋距离度量＋Schema 版本** 管理 Collection，不默认每个文档建 Collection。维度相同也不代表不同模型向量可比较；模型更换需新构建和明确路由。

默认共享 Collection，通过可信 tenant_id、kb_id 及索引代次过滤。高隔离要求可升级独立 Collection 或数据库，具体资源限制在部署选型时验证。Partition Key 可作为性能优化，不能替代业务授权。

| 字段 | 建议类型 | 用途 |
|---|---|---|
| vector_id | VARCHAR 主键，业务生成 | tenant/kb/index_generation/chunk/embedding 版本组合的稳定 ID，重复写入保持同一实体 |
| embedding | FLOAT_VECTOR，dim 按模型确定 | 稠密检索向量，写入校验维度及数值合法性 |
| tenant_id、kb_id | VARCHAR | 必填授权与检索范围过滤 |
| document_id、document_version | VARCHAR / INT64 | 关联原文及版本 |
| parse_revision、index_version | VARCHAR | 关联解析与分片/索引构建版本 |
| index_generation | VARCHAR | 知识库一次完整可发布的检索快照标识 |
| retrieval_chunk_id、parent_id | VARCHAR | 回查 PostgreSQL 正文、引用与父结构；无父级使用明确空值约定 |
| embedding_profile_version、content_hash | VARCHAR | 构建核对、缓存校验与模型来源 |
| chunk_type | VARCHAR | 可选内容类型过滤 |

核心过滤字段使用显式 Schema；大段正文、原图和完整 ACL 不复制到 Milvus。索引配置先以适配 embedding 的 COSINE 等度量做质量验证，ANN 索引类型及搜索参数按数据量、过滤选择性、内存、Recall 和 P95 压测决定，不假定单一参数适合所有租户。

设计参考：[Milvus Schema](https://milvus.io/docs/schema.md)、[数据模型](https://milvus.io/docs/schema-hands-on.md)、[Partition Key](https://milvus.io/docs/use-partition-key.md)。实际字段类型、限制与 SDK 调用以锁定版本为准。

### 3.3 构建、发布与一致性

PostgreSQL 与 Milvus 没有跨库原子事务，采用 **持久构建清单＋Outbox＋幂等写入＋可见性验证＋发布指针**：

1. 在 PostgreSQL 保存 RetrievalChunk、构建清单、期望 ID/内容哈希及 outbox，构建状态为 building。
2. 文档 Worker 在索引构建任务中按固定 embedding 方案批量编码，写入带 index_generation 的 Milvus 实体。批次记录成功/失败，重试使用稳定主键和明确 upsert 语义，不把重复 insert 当作业务幂等保证。
3. 核对向量 ID、数量、内容版本和失败清单；确认索引已就绪且在约定一致性级别下可检索。写请求成功不等于已经可用于正式检索。
4. 完成关键词与向量两路的同代次构建后，在 PostgreSQL 事务中用预期版本条件切换 active_generation。每次查询读取一次该指针，并固定本次两路检索版本。
5. 旧代次保留回退窗口，确认无在途读取后异步清理；取消、失败或未完成构建不能切换指针。

index_version 描述具体索引构建版本；index_generation 是知识库发布清单，明确其包含的各文档原文/解析/索引版本。初期按完整知识库快照构建，未变更内容可复用 embedding 缓存，但新代次仍需有完整可查记录。不能只写变更文档后切换全库代次，否则未变更文档会消失。大规模增量发布再引入有边界的有效版本清单和压实方案。

发布验证与在线查询显式选择并测试一致性级别。初期可采用 Strong 保证发布后读取要求，评估延迟后再制定受控放宽方案；Milvus 的一致性配置不替代跨库发布协议。参考 [Milvus 一致性说明](https://milvus.io/docs/consistency.md)。

### 3.4 检索链路与权限

```text
可信身份 → 获取知识库授权及 active_generation
    → 查询文本 embedding（与目标 Collection 模型版本一致）
    → Milvus 带 tenant/kb/generation 及授权范围过滤的 ANN 召回
    ＋ PostgreSQL 同代次关键词召回
    → 候选 ID 回查正文，复核当前权限、启停及版本
    → 按策略融合去重，必要时重排
    → 父子/句子窗口扩展，再校验权限与预算
    → 返回带原文位置和版本的引用
```

Milvus 过滤表达式由服务端根据结构化范围生成，不拼接未经校验的用户输入；查询和删改均强制包含租户条件。原始向量距离与关键词分数不直接相加，采用经过验证的排名融合或校准策略。

文档 ACL 能下推时在检索前过滤，复杂权限由授权服务提供受控范围，并在回查后再次验证。任何正文送往重排模型、生成模型或返回用户前都完成权限复核。过滤不足造成候选减少时使用有限补召回或明确结果不足，不无限扩大范围。

### 3.5 停用、删除与故障恢复

- 停用或撤权先在 PostgreSQL 生效，实时回查阻断旧向量结果，再异步更新/删除 Milvus 投影；不能等待向量删除才撤销访问。
- 物理删除记录受控删除任务，覆盖 Milvus 代次、正文及对象存储，区分普通停用、保留期清理与用户数据删除要求。
- Milvus 不可用时，按显式配置降级为关键词检索并标记 degraded，或返回可解释服务错误；不能伪装成“未找到知识”。
- 投影丢失可从 PostgreSQL Chunk 与固定模型方案重建；可选保存受权限控制的 embedding 产物以降低重新编码成本，需记录模型版本及校验和。
- 对账任务检查孤儿向量、漏写、错误代次及长期未完成批次；删除旧代次不能影响 active_generation 或仍在保留期的回退版本。

规划配置项包括 Milvus URI、服务凭据引用、TLS、Collection 映射、批量大小、超时、搜索参数和一致性级别。凭据仅留在后端，API/前端不开放任意 Collection 或过滤表达式操作；这些配置尚未加入现有 `.env`。

## 4. 接口与事件契约

以下 HTTP 路径均以 `/api/v1` 为前缀。目标方法、字段和事件为待实现契约，不能作为现有 API 调用。

当前接口：`GET/POST /knowledge-bases`、`GET/POST /knowledge-bases/{id}/documents`、`PUT /knowledge-bases/{id}/documents/{did}`、`PATCH /documents/{id}`、`GET /knowledge/search`。

目标契约：`search(context, query, scope, retrieval_options) -> SearchResult[]`；结果含 document_id、document_version、chunk_id、excerpt、score、source_ref、index_version。scope 由可信调用方结合授权生成，模型不能扩展范围。导入返回 job_id，任务查询与检索分离。

### 4.1 新增 Backend 异步接口（规划）

| 方法与路径 | 行为 |
|---|---|
| POST /knowledge-bases/{id}/imports | 验证已上传对象归属及完整性，幂等创建文档解析任务，返回 202 和 job_id |
| GET /knowledge-jobs/{job_id} | 阶段、已持久化页数、错误、重试和可用恢复能力 |
| POST /knowledge-jobs/{job_id}/cancel | 幂等申请取消，返回申请状态，不伪报 GPU 已停止 |
| POST /knowledge-jobs/{job_id}/retry | 校验版本/权限，根据 Parser 能力从检查点继续或整文档重试，明确返回恢复方式 |
| GET /knowledge-jobs/{job_id}/results | 按页范围/游标读取 JSON、Markdown 导出引用及部分失败信息 |
| POST /knowledge-bases/{id}/documents/{did}/publish | 校验完整解析与索引版本，原子切换在线引用 |

上传采用平台 storage 的直接上传或受控预签名流程，不接受任意外部 URL 作为内部下载指令。创建任务的幂等键与内容摘要绑定，不能因重试创建多份文档。

### 4.2 Parser 统一端口（规划）

逻辑契约为 `parse(file_ref, options) -> ParseResult`。输入包含经过校验的对象引用、真实格式、解析配置版本、job_id/attempt、幂等请求键、deadline、取消信号和可选 checkpoint；输出包含页信息、文本、表格、公式、图片引用、来源位置、警告及实际 Parser 版本。

支持渐进输出的适配器可用 `iter_pages(...)` 返回页结果与进度，结果协议保持一致。所有大产物以受控对象引用传递，禁止任意网络 URL 抓取；不支持渐进输出时返回完整产物引用，不伪造页进度。

对异步外部服务，适配器内部封装 submit/status/result/cancel，并持久化 provider_request_id。请求键在同一远端操作的查询重试中稳定，租约 attempt 用于本地提交校验；远端响应丢失后优先按请求键核查，不能仅因新的 attempt 就重复创建 GPU 工作。远端不支持幂等核查时，明确记录结果未知与重试风险。

Backend 无需统一规定 Parser 的 HTTP URL；Foil 如暴露 `/api/v2/parser/layout` 和 `/api/v2/parser/general`，由 Foil 适配器内部串接，对知识服务仍呈现一个解析端口。不会增加 Backend 的两套模型调用/调度 API。

首版必要端口为 `ParserAdapter`、`DocumentJobRepository`、`ArtifactStore`、`Chunker`、`IndexBuilder`。转换及渲染是适配器内部职责，复杂后再拆独立实现；所有适配器统一错误码、重试性及能力说明。

保留 `VectorStore` 及 Milvus 适配器：`upsert_batch(context, generation, records)`、`search(context, query_vector, scope, generation, options)`、`verify_generation(...)`、`delete_generation(...)`。索引构建在同一知识任务队列执行，通过持久批次清单恢复，不新增索引专属调度系统。

### 4.3 整体调用链路

```text
上传文件到 MinIO/S3 → 类型、对象归属及完整性校验
    → PostgreSQL 同事务创建文档版本与文档任务
    → 独立文档 Worker 领取并续租
    → 按格式选择 Parser 适配器（必要的转换由适配器封装）
    → 页面/批次结果及进度落库；或导入远端整文档产物
    → 标准化 ParseChunk，组装 JSON/Markdown
    → 默认混合分片，保存 RetrievalChunk 与关键词索引
    → 同队列执行索引构建，Embedding → Milvus
    → 完整性与权限校验 → 发布检索版本
```

关键词模式在 Milvus 接入前可独立运行，模式必须显式记录。解析结果可查询不等于在线索引已发布。规划事件包括 knowledge.import_created、knowledge.page_parsed、knowledge.parse_completed、knowledge.index_published、knowledge.job_failed，在业务提交后派发；事件不是第二套解析任务队列。

## 5. 依赖与职责边界

依赖身份/策略、文件存储，以及未来 embedding/rerank 模型端口。拥有文档与检索，不拥有最终答案；Runtime/Agent 决定如何使用检索结果。embedding 模型配置复用模型网关，不另存模型密钥。

| 组件 | 核心职责 |
|---|---|
| Knowledge Backend | 上传受理、权限/版本、创建任务、查询进度及发布 |
| 独立文档 Worker | 领取/续租、调用适配器、分批落库、分片及索引阶段编排 |
| Parser 适配器 | 格式路由、必要转换、统一输出；封装第三方 API、进度、取消及恢复差异 |
| 解析服务/推理后端 | 内部 OCR/视觉模型、Layout/General 等可选流程及 GPU 批处理 |
| PostgreSQL | 文档、任务队列、租约、页面、Chunk、版本及最终业务事实 |
| MinIO/S3 | 原文、页面图、转换/解析/导出产物 |
| Milvus | 向量及过滤字段、ANN 检索，可重建索引投影 |
| 模型网关 | Embedding/Rerank 及可直接调用的 OCR 推理、凭据、模型配置和用量规范 |
| 观测/评测 | 任务/解析端点指标、格式兼容性、解析与检索效果 |

本版不依赖 Redis 双层队列、独立 Layout/General Worker 池、自建 Worker 注册中心或 GPU 选址。复杂解析由接入服务封装；普通任务租约/owner 不是 Worker 注册中心。

先以 jobs、parsers、chunking、indexing、retrieval 划分代码职责，通过组合入口注入。文档 Worker 与客服 API/Runtime 进程隔离；不可信文件转换运行在受限进程/容器，心跳不被阻塞转换占用事件循环。SDK/解析服务按固定并发和超时调用，不能让多层重试相乘。

格式覆盖由适配器能力矩阵及验收语料决定，与平台是否自建 GPU 调度无关。后续只有在指标证明瓶颈后才扩展队列或页任务，不把这些预留组件作为首版依赖。

模型网关已将 Chat、Embedding、Rerank、语音（ASR/TTS）和 OCR 纳入规划，见[模型网关方案](../model_gateway/README.md)。Parser 可通过网关 OCR 端口执行页面/区域识别，文件转换、页级组织和结果标准化仍归 Parser。对于内部已封装模型的第三方解析服务，使用整体服务适配，不强行拆出不可见的 OCR 调用，也不重复记录模型费用。

## 6. 关键设计约束

- 在召回阶段和返回阶段落实访问范围，缓存键必须包含租户与授权范围。
- 文档更新完成前保留旧有效索引，新版本发布时原子切换，避免半份文档可见。
- 引用应固定内容版本，不能让历史回答链接悄悄指向新内容。
- 文档内容作为不可信数据，不得提升为系统指令或授予工具权限。

### 6.1 可靠性、取消与恢复

- PostgreSQL 原子领取/续租，所有阶段提交验证 owner、attempt、lease 和 cancel_requested，拒绝迟到 Worker；远端推理可能仍运行，但不能提交本地成功状态。
- 页面结果和检查点同事务保存，以文档版本、解析版本、页号和元素序号约束重复；检查点指向已校验产物，不仅是页号计数。
- 支持续跑的 Parser 从有效检查点恢复；不支持则整文档重试。非确定性重解析不能覆盖已有冻结结果或将新旧页混合发布，必要时创建新的 parse_revision，并保留旧失败尝试记录。
- Worker 崩溃或数据库暂时不可用后，由租约回收恢复任务；索引批次持久化并校验模型版本。任务终态或索引发布失败时，现有在线知识版本保持可用。
- 取消停止新阶段、向适配器传播并使检查点/结果提交受限；不支持远端取消时明确显示该限制，防止取消后的任务继续发布索引。
- 结果对象上传与数据库提交无法跨系统原子完成，采用稳定对象标识、内容校验和孤儿清理；重试不无限创建文件。
- 文档任务和索引构建都遵守有限 attempt 与截止时间；失败页可预览，但完整性不满足时不能发布。

### 6.2 资源、隐私与格式安全

- 对文件大小、页数、像素数、解压体积、转换耗时、CPU/内存、GPU 并发和总预算分别设限，实施前确定可配置默认值。
- 文档转换器在隔离 Worker/容器内运行，禁用宏、外部资源加载及非必要网络；这是不可信文件解析隔离，不代表普通客服 API 工具需要代码沙箱。
- 对象路径与结果查询按租户授权；附件通过短时授权访问，不公开持久 bucket URL。对象删除、保留期限及任务日志脱敏统一管理。
- 表格 HTML、Markdown 和文档预览内容按不可信内容处理，禁止脚本及危险链接在管理台执行。
- OCR 模型产生的内容可能有误；原页图、模型版本和来源区域保留，重大解析警告进入复核，不直接发布为可信业务结论。

### 6.3 检索及质量保障

新索引保留标题路径、表格上下文和来源映射。向量模型或切分策略变化生成新 index_version；查询向量必须与索引使用相同兼容模型配置，不能混用维度。缓存包含租户、授权范围及索引版本。

分别验证文本识别、布局/阅读顺序、表格结构、公式、坐标引用与下游检索命中；不能用“最终回答听起来合理”替代解析质量验证。LLM-as-a-Judge 可辅助检查证据一致性，但页面范围、坐标合法性、引用版本及任务幂等仍采用确定性检查。

### 6.4 分片策略效果对比

使用相同文档版本、问题集、权限范围和检索配置比较策略；比较边界算法时尽量固定 embedding/重排模型及实际返回的上下文 Token 预算，单独记录必须变化的参数。固定字符基线、递归方案、结构混合方案先形成可复现对照。

评价包括：证据覆盖 Recall@K、排序质量、答案正确性与依据一致性、引用定位、重复内容比例、超长/过短片比例、索引体积、生成索引耗时、调用费用及检索 P95。K 相同时片段大小不同会影响信息量，因此同时比较固定上下文预算下的效果。

按文档类型和问题类型分组，重点包含跨页条款、条件/例外、表格数值、同义表达及长距离指代；不能只看全库平均值。标注证据使用原文范围，避免绑定某一策略的 chunk_id。父子/窗口扩展后的最终上下文也需评估噪声、重复及授权正确性。

LLM-as-a-Judge 按 evaluation 模块的校准规则评价回答，不用向量相似度直接证明分片有效。语义切分、生成背景、Late Chunking 只有在保留测试集显示收益且成本可接受后才扩大使用。

## 7. 管理台规划

管理台按以下工作区建设：

- **知识库与导入**：格式支持说明、上传、配置选择、版本及权限。
- **任务中心**：排队/阶段状态、页级进度或整文档进度、失败范围、重试、取消及实际支持的恢复方式；首版不提供优先级调度配置。
- **解析预览**：原页与结构化内容对照、bbox 高亮、阅读顺序、表格/公式/图片及警告。
- **结果导出**：分页 JSON、Markdown、附件授权访问及部分失败说明。
- **版本与发布**：原文/解析/索引版本、差异、纠错重建、完整性校验与回退。
- **检索验证**：关键词/向量/融合结果、引用定位、权限和索引版本。
- **分片策略**：基础算法与增强组合、参数校验、逐片预览、父子关系、Token 分布、超长告警及版本发布；尚不可用策略明确标识。
- **策略对比**：同文档不同配置的边界、召回证据、回答质量与成本对比，支持选择重建和回退索引。
- **运维与质量**：文档队列积压、Worker/解析端点健康、阶段耗时、重试率、服务用量及存储质量指标；不建设 GPU 实例管理台。

界面权限与后端校验保持一致；配置区分草稿和生效版本。加载、空数据、冲突、拒绝和失败均有明确反馈，未实现操作不显示为可用。

## 8. 实施阶段

- P0-A：冻结 Parser 端口/能力矩阵、页面结果与版本协议，建立 PostgreSQL 单队列及独立 Worker，接入 MinIO/S3 和假 Parser，验证租约、幂等、重试、取消。
- P0-B：接入真实适配器，逐项完成 PDF、Word、RTF、ODT、PPT/PPTX、Excel、PNG/JPG/JPEG、OFD、CAJ、XPS 的兼容性验收；保留 TXT/Markdown。适配器可逐项交付，但完整格式验收是本版交付条件，不因简化调度裁剪。
- P0-C：完成结构化结果、页级进度/整文档降级、导出与来源映射；默认混合分片、递归兜底，关键词索引及可控版本发布。
- P0-D：接入 embedding 和 Milvus，沿用同一知识任务队列，验证批次幂等、构建完整性、发布回退和权限过滤，完成端到端检索。
- P1：根据评测扩展分片策略目录、父子/窗口增强、融合重排、复杂跨页质量、细粒度 ACL 和运营能力。完整功能目录保留，首版不要求实现所有高级算法。
- 后续调度扩展：只有实测需要时才引入页任务并行、Redis 或跨 GPU 资源调度，另行给出容量收益与迁移设计。

原 Milvus“P1 再接入”调整为 P0-D，确保本版具有向量检索闭环。分片专项首版聚焦混合＋递归/固定基线，其他策略按目录渐进实施；保留原文、解析和索引版本体系。

首版需提供一套实际可运行的配置：解析端点/格式矩阵、Worker 数量及并发、上传/页数限制、租约/心跳、重试次数、deadline、分片预算及 embedding/Milvus 参数。具体值依据所选后端与样例测定，不承诺未经测量的吞吐或 P95。

每阶段先验证端口、假实现及数据库不变量，再集成真实服务。格式转换器许可和依赖必须明确；某项格式未就绪就列为交付缺口，不能仅允许扩展名上传便宣称支持。

## 9. 独立开发验收

- 不同租户、停用文档和无权知识库不出现在结果中。
- 文档更新后仅当前有效版本参与在线检索，历史引用仍可追溯。
- 任务重试不会重复索引，同一版本重建可核对一致性。
- 假 embedding 及固定语料即可独立验证排序融合；真实库验证权限过滤。
- 使用 100 页样例验证一个文档任务的页面覆盖完整、结果按页号/seq 导出、内存有界，且未生成独立页面队列任务。
- 验证扫描、旋转、多栏、表格、公式、图片及跨页样例，结果能回指正确页图与区域；Excel 保留原生单元格与公式信息。
- 对每个声称支持的格式提供成功、损坏、加密及超限样例；不支持格式返回明确错误。
- 模拟 Worker 崩溃、数据库短暂不可用、远端响应丢失、对象上传后提交失败，任务可按租约恢复且不重复落库；不依赖 Redis 恢复。
- 模拟取消与结果提交竞争，取消后不能发布新索引；失效租约/旧 attempt 的迟到结果被拒绝。
- 文档任务部分失败时返回失败页和实际支持的恢复方式，不能展示 100% 成功或发布残缺索引。
- 分别测试支持检查点恢复和仅支持整文档重试的 Parser，两者均如实展示恢复能力，避免混合不同解析版本页面；无需暴露 Layout/General 调度。
- 使用假 Parser 验证编排、队列与 Schema，真实模型使用标注语料验证内容质量；两类验证不可替代。
- 在专用环境验证 PostgreSQL 独占领取、租约回收、唯一约束及 S3 兼容存储权限；知识任务不占用客服 Runtime 并发，测试数据不得进入生产知识库。
- 在专用 Milvus 环境验证租户/kb/generation 过滤、维度校验、批量幂等写入及发布可见性，不能只依赖内存向量库测试。
- 模拟 PostgreSQL 已提交但 Milvus 写入失败、向量写入成功但确认丢失、发布竞争及部分构建失败，均可恢复且不会发布残缺索引。
- 修改一个文档后发布新知识库代次，未修改文档仍可检索；旧代次回退正确，清理不删除当前生效代次。
- 撤权和文档停用后，即使 Milvus 仍有旧向量，也不能把正文送往重排/生成模型或返回用户。
- Milvus 故障时按配置展示关键词降级或明确错误，恢复后通过对账重新启用；不能把向量故障统计为正常零命中。
- 所有分片策略保留 source_chunk_ids 及原文定位；合并、重叠、跨页和父子扩展后仍可回溯，不混合租户或文档版本。
- 长句、极短段落、超长表头、单行超宽表格和中文标点都有确定的处理结果；不能静默丢弃内容或出现切分不前进。
- 实际索引文本包含附加标题/表头/背景后仍满足 Token 上限；模型或 tokenizer 不兼容时发布失败，不静默截断。
- 父子及句子窗口扩展重新验证权限、去重并遵守上下文预算，不能通过父章节读取未授权内容。
- 生成背景与原文分开呈现；背景错误、注入或缺失时有明确降级行为，不能伪装为原文引用。
- Late Chunking 只在适配器声明并验证能力后可选；超窗口输入、跨度映射错误和普通 embedding 接口不支持的情况可解释失败或按显式策略回退。
- 同一配置/算法版本的确定性切分可复现；语义/生成增强保留实际结果与模型版本。配置改变创建新索引并可回退，不重新污染解析层。

上述为目标验收条件，不是已有测试覆盖声明。已验证范围参见项目 `docs/platform-validation.md`。交付需更新本节对应测试位置及第 1 节实现状态。

可选语义分片已实现：默认 hybrid 不变，semantic 使用模型网关 Embedding 固定版本与相似度阈值；分页预览、保存复用 PostgreSQL 缓存。详见 docs/knowledge-workspace.md。

分片预览现由 PostgreSQL 队列与独立 Worker 执行，支持任务进度、取消、完成结果分页读取；工作台每 2 秒刷新并保留手动刷新入口。取消在处理检查点生效，不支持暂停续跑。迁移：0024_chunk_preview_tasks。
