# 客服业务与流程（customer_service）

将客户意图转换为可验证的业务流程，负责消息路由、业务确认、工单和外部办理结果。

本文是模块开发规划。当前实现以第 1 节和代码为准，其余内容为目标设计；P0/P1 表示建设优先级，不表示已经完成。跨模块约定见[独立开发规范](../../../../../docs/module-development.md)，全局索引见[模块架构](../../../../../docs/architecture.md)。

## 1. 当前实现与差距

已实现工单提议、人工确认、幂等业务动作及工单状态流转；新增 ticket_lookup，只能查询当前租户和当前会话的工单。Agent 不能把提议直接当成成功写入。通用外部 CRM/订单适配、写操作补偿和复杂业务审批尚未实现。

目标工单设计已采用 **tickets 固定列＋tickets_detail.custom_fields JSONB＋ticket_process_log 追加记录**，配套类型版本和字段选择，详见 [通用工单设计 v1](TICKETING.md)。0008_ticketing 已准备表结构、一次性回填及旧列删除；现有创建/查询/状态接口直接使用新结构。类型设计器、JSONB 字段编辑及校验尚未实现，目标数据库需执行升级。

## 2. 功能模块与优先级

P0：独立开发及稳定集成所需基础能力。P1：规模化、治理或复杂场景扩展。按现有能力增量交付，不重复重建已实现功能。

| 功能模块 | 功能点 | 优先级 |
|---|---|---|
| 服务路由 | 自动服务、人工队列、关闭会话的确定性处理 | P0 |
| 业务能力目录 | 查询、拟定、确认、执行的边界和风险等级 | P0 |
| 信息收集 | 必填字段、格式校验、补充询问及业务前置条件 | P0 |
| 待确认动作 | 不可变操作内容、有效期、确认者权限、拒绝与冲突 | P0 |
| 工单生命周期 | 创建、修订冲突、处理、解决及关闭规则 | P0 |
| 外部办理 | 订单/CRM/退款适配、幂等键、状态查询及结果核查 | P1 |
| 长事务流程 | 步骤状态、外部回执、超时、补偿及人工处理 | P1 |
| 业务规则版本 | 流程定义、适用范围、发布版本与历史追溯 | P1 |
| 业务运营 | 服务分类、处理时限、满意度、结果统计 | P1 |

## 3. 数据与状态归属

现有 `pending_actions`、`tickets`。待确认动作当前为 pending/confirmed/rejected，超期按 expires_at 判断；工单为 open/in_progress/resolved/closed。目标新增 tickets_detail、ticket_process_log、ticket_types、ticket_type_versions；业务字段使用有 Schema 约束的 JSONB，通用字段仍为固定列。外部操作账本后续建设。

现有表由已提交的 Alembic 迁移管理；本规划不创建新表。未来扩展使用新增迁移，避免修改已应用历史迁移。跨模块数据先明确所有者，再增加服务端口。

## 4. 接口与事件契约

以下 HTTP 路径均以 `/api/v1` 为前缀。目标方法、字段和事件为待实现契约，不能作为现有 API 调用。

当前接口：`POST /conversations/{id}/messages`、`POST /actions/{id}/decision`、`GET /tickets`、`PATCH /tickets/{id}`。内置 propose_ticket 只生成待确认项。

目标契约：`propose_action(context, ActionSpec) -> PendingAction`、`decide_action(context, action_id, decision, expected_revision)`、`query_operation(context, operation_id)`。动作含业务类型、参数摘要/哈希、作用对象、有效期和幂等键；返回明确已确认、已执行或结果未知状态，不能混为成功。

## 5. 依赖与职责边界

[platform_settings](../platform_settings/README.md)（规划）只定义工单模式与停用流程及其层级规则；本模块继续拥有工单事实、确认规则和存量处理。默认队列等业务配置不转移到平台设置，当前未实现工单模式开关。

依赖 conversation、Agent 快照、Runtime 提交、人工协同及工具执行端口。拥有业务规则和确认状态；工具网关只执行已获授权的请求，模型不能直接改变订单或工单状态。

独立开发不要求立即拆成微服务。先定义 Protocol/DTO 与假实现，由组合入口注入；新增跨模块调用不直接导入对方仓储。当前共享事务例外见独立开发规范。

## 6. 关键设计约束

- 确认必须绑定原始参数和资源；修改金额、对象或内容后需生成新的确认。
- 重复确认返回同一业务结果；外部超时可能已成功，先查询结果再决定重试。
- 当前本地工单可在数据库事务内原子完成；外部系统须用操作账本和补偿策略。
- 操作确认者来自可信身份，不接受模型或客户端自报管理员权限。

## 7. 管理台规划

工单提案卡片、确认/拒绝、工单列表、状态与备注；后续增加外部办理进度、异常补偿及业务规则管理。

界面权限与后端校验保持一致；配置区分草稿和生效版本。加载、空数据、冲突、拒绝和失败均有明确反馈，未实现操作不显示为可用。

## 8. 实施阶段

- P0：按 [通用工单设计 v1](TICKETING.md) 建设类型版本、JSONB 详情、追加处理记录、负责人及待客户补充状态；保留确认创建语义，按开发阶段直接切换表结构和服务，不维护旧代码兼容层。
- P1：选择一个真实业务系统接入，先实现幂等及核查，再扩展多步骤流程。

每阶段先冻结最小接口与验收用例，再实现领域服务、持久层、API 和页面；集成时验证与上下游的兼容性。

## 9. 独立开发验收

- 并发确认只创建一张工单，过期或已拒绝动作不能继续执行。
- 参数修改后旧确认不能授权新操作。
- 模拟外部接口超时但已成功时，不重复办理并可查询恢复。
- 假业务适配器可覆盖成功、拒绝、部分成功及结果未知状态。

上述为目标验收条件，不是已有测试覆盖声明。已验证范围参见项目 `docs/platform-validation.md`。交付需更新本节对应测试位置及第 1 节实现状态。
