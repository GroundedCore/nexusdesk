# Phase 4 · 治理与标记记忆 — 业务目标

> 阶段：Phase 4
> 预估工期：~1-2 周
> 依赖：Phase 2/3（可在 Phase 3 之后或与其并行后半段）

## 要解决的问题

### 问题 1：错误记忆缺乏完整治理闭环

Phase 2 提供了编辑/删除入口，但生产环境还需要：错误记忆的纠正如何传播、冲突如何审计、人工修改与自动抽取打架怎么办（坐席改完，下一轮抽取又改回去）。

### 问题 2：VIP / 风险客户无标记能力

客服运营需要给特定客户打标（VIP 优先服务、投诉高风险、黑名单），并让 Agent 在对话中体现差异化服务策略。这类标记**绝不能由 LLM 自动抽取**（误判代价高），必须人工或规则写入。

### 问题 3：合规要求未闭环

记忆中的手机号、证件号等 PII 需要脱敏；客户行使删除权（"忘记我"）时，需要级联清理 PG 行与向量数据，并留审计。开放平台客户删除、企业用户离职等场景也会触发。

### 问题 4：记忆无衰退机制，准确率随时间单调下降

记忆不是越久越值钱。客户搬家了旧地址还在、承诺早已兑现还被引用、三年前的琐事挤占注入上限——没有衰退机制，记忆系统上线越久错误越多，与建设初衷背道而驰。同时纯 TTL（Phase 3 的 180 天硬过期）过于粗暴：客户每月都在用的偏好不应因"条目创建于一年前"而被遗忘，需要"使用让它保值"的强化机制配套。

### 问题 5：记忆质量无观测

抽取准确率、记忆命中率、pending 积压量目前无处可查，无法持续运营改进。

## 业务目标

| 目标 | 说明 |
|---|---|
| G1：人工纠正优先 | 人工编辑过的记忆不被自动抽取覆盖，形成"人工 > 自动"的明确优先级 |
| G2：标记记忆 | 支持 VIP / 投诉风险 / 黑名单三类标记，仅人工/规则可写，注入优先级最高 |
| G3：合规闭环 | PII 脱敏入库；客户删除 API 级联清理并可审计 |
| G4：记忆保鲜 | 时间让低价值记忆贬值（置信度衰减 + 软过期），使用让高价值记忆保值（引用强化），人工记忆免疫衰退 |
| G5：质量可观测 | 记忆运营指标进入现有观测体系，支持持续改进 |

## 成功指标

| 指标 | 目标 |
|---|---|
| 人工编辑的记忆 30 天内被自动抽取覆盖的比例 | 0% |
| 客户删除请求的执行完整性（PG + 向量无残留，自动化校验） | 100% |
| 记忆条目 PII 脱敏覆盖率（手机号/身份证/银行卡模式） | ≥ 99% |
| 注入条目的"保鲜度"（注入集中 90 天内被引用过的条目占比） | ≥ 80% |
| 衰退误伤率（被过期条目 30 天内被人工恢复的比例，越低说明衰退越准） | ≤ 5% |
| 观测页记忆指标可用 | 抽取量 / 命中率 / pending 积压 / 删除执行 可查 |

## 范围

**包含**：
- 人工保护机制（`source_type='human'` 条目免疫自动覆盖）；
- 标记记忆（type=`flag`）：三类受控标记 + 规则引擎写入（如"工单 48h 未响应自动标风险"）+ 最高优先注入；
- PII 脱敏（入库前对 content 做模式脱敏，原值不落库）；
- 客户删除 API（"忘记我"）：级联删除 identities/items/embedding，会话 `customer_id` 置空，审计留痕；
- 跨渠道身份人工合并（控制台操作，两个 customer 合并为一，记忆归并）；
- 衰退机制：按类型差异化的置信度衰减、引用强化、容量淘汰（全部软过期可恢复）；
- 记忆运营观测指标（接入 `ObservabilityService`）。

**不包含**：
- 记忆的多级历史版本管理（当前 `prev_content` 单级历史，视运营需要后续再扩展）；
- 面向终端客户的"我的记忆"自助页面（渠道侧能力，后续单独立项）。

## 风险与约束

- **删除的彻底性**：向量数据（pgvector 列）随行删除即清除；但若未来切 Milvus 需同步删除 collection 数据——`MemoryStore` 接口需补 `delete_customer(customer_id)` 方法预留。
- **合并的不可逆性**：客户合并是不可逆操作，控制台需二次确认 + 完整审计日志。
- **规则引擎克制**：Phase 4 仅支持 2-3 条内置硬编码规则（超时未响应标风险等），不做通用规则配置界面，避免范围蔓延。
