# Phase 3 · 事件记忆 + 语义检索 — 业务目标

> 阶段：Phase 3
> 预估工期：~2 周
> 依赖：Phase 2 的客户实体与 `memory_items` 表

## 要解决的问题

### 问题 1：工单与记忆不联动

平台已有完整的工单生命周期（propose → 人工确认 → 状态机流转 → resolved/closed），但这些结果对 Agent 完全不可见。典型受损场景：

- 客户上周的工单已解决，本周再次进线，Agent 不知道处理结果，给出与上次矛盾的建议；
- 坐席在工单中承诺"48 小时内退款"，客户三天后来问进度，Agent 不知道这个承诺的存在；
- 同一问题重复开单：Agent 无法感知客户已有在途工单（虽有 `ticket_lookup` 工具，但需 Agent 主动调用且不知道客户身份维度）。

### 问题 2：记忆增长后全量注入不可持续

Phase 2 的画像/偏好条目有限（20 条上限足够），但事件类记忆随服务历史持续增长。全量注入 prompt 会挤占上下文、稀释注意力，需要"按需检索"能力。

## 业务目标

| 目标 | 说明 |
|---|---|
| G1：工单闭环可见 | 工单的创建、解决、关闭自动沉淀为该客户的事件记忆，Agent 在后续对话中可用 |
| G2：承诺可追踪 | 工单/对话中的承诺事项（退款时限、回电约定）以事件记忆留存，客户追问时 Agent 能引用 |
| G3：按需检索 | 提供 `memory_search` 工具，Agent 针对当前问题主动检索该客户的历史事件，不占用常驻 prompt 空间 |
| G4：部署承诺不破 | 无 Milvus 的两容器环境功能完整可用（降级检索），生产不新增中间件类组件（memory-worker 容器复用后端镜像，为 Phase 1 修订后的既定拓扑，见 `../../phase-1-conversation-summary/03-technical-design.md` §核心流程3） |

## 成功指标

| 指标 | 目标 |
|---|---|
| 回头客会话中 Agent 正确引用历史工单结局的比例（评估集） | ≥ 80% |
| `memory_search` 检索相关性（人工抽检 top-3 命中） | ≥ 85% |
| 事件记忆写入延迟（工单状态变更 → 记忆可查） | ≤ 1 分钟 |
| 无 Milvus 环境（TSVECTOR 降级）检索相关性 | ≥ 70% |
| 事件记忆 TTL 过期任务正常执行 | 过期条目不进入检索与注入 |

## 范围

**包含**：
- 事件记忆（type=`event`）：工单生命周期事件自动写入（创建/解决/关闭/承诺备注）；
- 向量检索：pgvector 为主实现，TSVECTOR 为降级实现，`MemoryStore` 接口隔离；
- 内置工具 `memory_search` 接入 PlatformTools；
- 事件记忆 TTL（默认 180 天）与过期清理任务；
- 重要事件（如未解决工单、未兑现承诺）的常驻注入（少量高优条目）。

**不包含**：
- 标记记忆（VIP/风险）与人工打标（Phase 4）；
- PII 脱敏与"忘记我"级联删除（Phase 4，但本阶段表结构与删除接口预留）；
- 跨客户聚合分析（属于知识库/报表范畴，不属记忆系统）。

## 风险与约束

- **pgvector 引入决策**：需要 compose 镜像从 `postgres` 换成 `pgvector/pgvector`（同版本 PG）。这是本阶段唯一的中间件/镜像级基础设施变更，需评审确认；不接受的替代方案是仅用 TSVECTOR，检索质量下降但功能完整。（生产 memory-worker 容器复用后端镜像，非中间件级变更。）
- **事件噪音**：不是所有工单动态都值得成为记忆。仅写入：工单创建（含问题摘要）、解决（含解决方案摘要）、关闭、以及人工标记为"承诺"的备注；状态机的中间流转不写入。
- **注入预算**：常驻注入的事件条目 ≤ 5 条（未解决/未兑现类），其余完全依赖工具检索。
