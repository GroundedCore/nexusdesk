# Phase 1 · 会话摘要记忆 — 需求文档

## 用户故事

**US-1（终端客户）**：作为与客服 Agent 进行长对话的客户，我希望 Agent 记得我开头说过的关键信息（过敏史、故障现象、订单号），不必重复提供。

**US-2（人工坐席）**：作为接管会话的坐席，我希望看到一份完整的对话摘要加上最近的原始消息，快速理解客户诉求的全貌，而不是只有最近 10 条碎片。

**US-3（租户管理员）**：作为平台管理员，我希望摘要功能可以按租户/按 Agent 关闭，以控制 LLM 成本或满足特定合规场景。

**US-4（平台运维）**：作为运维人员，我希望摘要生成失败时不影响正常对话，系统降级为原有的滑动窗口行为。

## 功能需求

### FR-1 摘要生成

| 项 | 说明 |
|---|---|
| 触发时机 | run 结束写回 history 时，若本次发生了历史截断（被丢弃消息数 > 0），生成一次滚动摘要 |
| 输入 | 旧摘要（可空）+ 本次被丢弃的消息 |
| 输出 | 新摘要（自然语言段落，≤ 500 字），覆盖写回会话 |
| 执行方式 | **异步**：不阻塞 run 完成与回复返回；生成完成前，下一轮对话沿用旧摘要 |
| 失败处理 | 生成失败保留旧摘要，记录 warning 日志与审计事件，不重试超过 2 次 |
| 摘要内容要求 | 保留：客户身份信息、诉求/问题、关键事实与约束、已达成的结论、待办承诺；丢弃：寒暄、重复表述、工具调用细节 |

### FR-2 摘要注入

| 项 | 说明 |
|---|---|
| 注入位置 | 消息序列中 `SystemMessage` 之后、历史消息之前，作为一条 system 角色消息 |
| 注入格式 | 固定模板：`【此前对话摘要】\n{summary}`，空摘要时不注入 |
| 长度上限 | 注入前截断至 800 tokens（超出部分取摘要末尾，近期信息优先） |
| 对评估的影响 | evaluation 模块跑 case 时使用空历史，摘要注入为空，不影响现有评估 |

### FR-3 人工接管摘要

| 项 | 说明 |
|---|---|
| 现有行为 | 取最近 10 条消息拼接 |
| 新行为 | `滚动摘要（若有）+ 最近 10 条消息` 拼接为 handoff summary |
| 兜底 | 无摘要时行为与现状一致 |

### FR-4 配置开关

| 配置项 | 层级 | 默认值 | 说明 |
|---|---|---|---|
| `summary_enabled` | 全局 settings | `true` | 平台级总开关 |
| `summary_enabled` | AgentConfig | `true` | Agent 级开关，跟随草稿/发布/回滚 |
| `summary_max_input_messages` | 全局 settings | `40` | 单次摘要最多输入的被丢弃消息数（超出时先截断再摘要） |

### FR-5 可观测

- 每次摘要生成记录审计事件（conversation_id、输入消息数、摘要前后长度、模型用量）；
- 观测页 run trace 中可见"摘要已更新"标记。

## 非功能需求

- **性能**：摘要生成全程异步，对 run 的端到端延迟增加为 0；
- **兼容**：新增字段为空时，所有行为与现状完全一致；
- **多租户**：摘要存储在会话行上，天然继承 `tenant_id` 隔离，无跨租户泄露面。

## 验收标准

| # | 场景 | 预期 |
|---|---|---|
| AC-1 | 构造 25 轮对话（history_turns=10），第 1 轮声明"订单号 A123，对花生过敏"，第 25 轮问"推荐零食" | Agent 回复排除花生制品，且能引用订单号 |
| AC-2 | 上述对话转人工 | 坐席看到的 handoff summary 包含订单号与过敏信息 |
| AC-3 | 关闭 Agent 级 `summary_enabled` 后重复 AC-1 | 行为与现状一致（早期信息丢失），无摘要产生 |
| AC-4 | mock 摘要模型返回错误 | 对话正常完成，旧摘要保留，日志与审计有记录 |
| AC-5 | 新会话前 10 轮内（未发生截断） | 不产生任何摘要调用，无额外模型用量 |
| AC-6 | 摘要长度超过 800 tokens | 注入时被截断，不撑爆模型上下文 |
