# Phase 6 · 客户记忆可视化与注入可解释性 — 业务目标

> 阶段：Phase 6
> 预估工期：~1.5-2 周
> 依赖：Phase 1-4（已上线）；建议在 Phase 5 之后或并行（配置项影响展示字段，无硬依赖）

## 要解决的问题

### 问题 1：记忆"看得见"但"看不懂"

`frontend/src/features/memory/` 已有一版基础界面（客户列表、客户详情、记忆条目表、待确认队列、会话工作台记忆抽屉），可以查到具体用户的记忆。但运营与客服主管的日常问题回答不了：

- 这个客户的记忆全景是什么（各类多少条、多少待确认、最近什么时候更新）？
- 这条记忆从哪来、被谁改过、改过几次、之前是什么内容？
- 这条记忆最近有没有被用到？

### 问题 2：注入不可解释——"这次对话到底用了哪几条记忆"

当前 `memory.injected` 运行时事件只记条数（`{items, flags, events}`），不记具体注入了哪些 `memory_item_id`。当 Agent 回复出错或答非所问时，无法回溯"是不是某条错误记忆导致的"，排障只能靠猜。这是记忆可解释性的关键缺口。

### 问题 3：治理操作历史分散

编辑、确认/拒绝、衰退迁移、淘汰、合并、删除都写了 `audit_records`，但前端没有按客户/按条目的审计时间线视图，运营无法在界面上还原一条记忆的完整生命周期。

## 业务目标

| 目标 | 说明 |
|---|---|
| G1：三层记忆视图 | 客户总览（列表层）→ 客户详情（Tab 层）→ 单条记忆详情（生命周期层），逐层下钻 |
| G2：注入可解释 | 每次 run 注入了哪些记忆条目（id、小节、得分）可查询、可回溯，支持从会话反查、从条目正查 |
| G3：生命周期可还原 | 单条记忆的创建/变更/确认/衰退/恢复/合并/注入历史在一个时间线视图中完整呈现 |
| G4：运营效率提升 | 待确认处理、错误记忆定位、误注入排障的平均耗时显著下降 |

## 成功指标

| 指标 | 目标 |
|---|---|
| 注入明细落库覆盖率 | 100% 的 `memory.injected` 事件伴随明细记录（run × item 级） |
| 排障回溯能力 | 任意一次对话可列出当次注入的全部记忆条目及来源；任意条目可列出最近被注入的会话 |
| 单条记忆生命周期完整度 | 创建/编辑/确认/衰退/恢复/合并/注入事件在详情页时间线齐全（有审计即有点） |
| 误注入排障耗时 | 从"翻日志"降为界面操作 ≤ 5 分钟定位（UAT 情景计时） |
| 性能 | 客户详情页各 Tab P95 首屏 ≤ 1.5s（万级条目客户）；注入记录查询 P95 ≤ 2s |

## 范围

**包含**：

- `memory_injection_log` 明细表：run × item 级注入记录（含小节、得分、时间）；
- 注入埋点扩展：`memory.injected` 事件 payload 补充 item_id 列表（保持既有计数字段兼容）；
- 记忆总览层增强：客户列表补充记忆统计列（各类条数、待确认数、服务标记、最近更新）；
- 客户详情 Tab 重构：概览/画像/偏好/事件/服务标记/待确认/注入记录/审计记录；
- 单条记忆详情：完整字段展示 + 内容 diff（`prev_content` vs 当前）+ 生命周期时间线 + 来源会话/工单跳转 + 最近注入记录；
- 会话工作台联动：会话视图可查看当次 run 的注入明细（哪些记忆影响了本次回复）。

**不包含**：

- 多级历史版本管理（沿用 `prev_content` 单级历史 + 审计还原，不建版本表）；
- 注入明细的实时推送（页面查询即可，不做 WebSocket 实时流）；
- 面向终端客户的"我的记忆"自助页面（渠道侧能力，同 Phase 4 边界）；
- 记忆数据的图表化分析（趋势图、分布图属 Phase 7 观测范畴）。

## 风险与约束

- **写放大**：注入明细为 run × item 级写入，高频对话场景下需批量插入 + 保留期管理（默认保留 90 天，随 TTL 任务清理），不得在 run 热路径逐条 INSERT；
- **审计不含 PII 的红线不破**：详情页展示的审计时间线渲染自 `audit_records`，其 payload 本就不含记忆明文（Phase 4 C4），时间线不得引入新的明文泄露面；
- **存量数据**：上线前的历史 run 无注入明细，界面需优雅展示"该会话无注入明细记录"而非报错；
- **权限**：注入记录与审计记录含运营敏感信息，viewer 只读、不可见原始会话内容越权信息，租户隔离红线不变。
