## 背景

NexusDesk 的客服主链路已经可以跑通：知识检索 → Agent 推理 → 工具调用 → 人工接管 → 工单草拟与人工确认。`implementation-progress.md` 记录了 12 个模块的首轮交付，同时也写明「**不表示各 README 的全部 P0 已验收**」。

当前缺的不是功能，而是**工程保障**。以下问题在现有实现中都还没有明确答案：

- 工具授权的判断依据，究竟是服务端建立的身份，还是模型 / 调用方提交的字段？
- 需要人工确认的写操作，模型能不能通过换参数、换工具名或换调用路径绕过去？
- 外部写操作在超时、Worker 丢失或本地崩溃时，会不会被重试成两次副作用？
- 客户端因网络重试重复提交同一个逻辑 Run，会不会创建出两个 Run？
- Run 被取消、队列过期、Worker 丢失时，最终状态是否确定？过期 Worker 会不会覆盖新结果？
- 知识入库返回成功，是否等于内容已经可以被检索到？
- CI 只验证了正常流程，还是也覆盖了授权、幂等、取消、恢复这些故障路径？

本目录是 P0 生产就绪的规划与验收文档。七项要求各自对应一个 GitHub issue，可按项独立评审、独立排期。

## 文档边界（必读）

1. 本文档集**定义要求**，不记录实施进度，也不统计完成百分比。
2. 每项要求的**逐条验收与勾选，唯一权威是 GitHub issue**（#32–#38），本目录只写判断依据、范围与边界。
3. 状态变化走 issue；需求或范围变更走本目录的 PR，再同步到对应 issue。
4. **不得以「代码已实现」作为完成依据**。P0 保障必须同时具备：明确的契约、可强制执行的行为、可观测的结果、防止回归的自动化测试。

## 总体原则

1. **契约优先**：每项保障先定义契约（谁、在什么条件下、能做什么），不依赖约定俗成的实现细节。
2. **可执行**：契约必须在代码路径上强制执行，不能只写在文档里。
3. **可观测**：拒绝、失败、恢复均需结构化记录，运维能还原「为什么」。
4. **可回归**：每项保障都要有自动化测试覆盖，尤其是故障路径。
5. **复用优先**：沿用现有 `policy` / `tool_gateway` / `agent_runtime` / `knowledge` 的抽象；不得重复建设已有子系统。
6. **失败即关闭**：上下文缺失、审批无效、状态不确定时默认拒绝，而不是默认放行。
7. **单一权威**：进度只在 issue，本目录不复制勾选清单。

## 依赖与实施顺序

顺序为依赖关系，不要求严格串行。

- **第一阶段 — #32 可信执行上下文。** 是 #33、#34 的前置：确认与账本都需要可信的操作身份。
- **第二阶段 — #33 / #34 / #35 / #36 / #37，可并行。**
  - #33 依赖 #32；与 #34 协同，避免重试与结果不确定场景重复产生外部副作用。
  - #34 依赖 #32；与 #33 协同，保证已审批操作的身份绑定与防重放。
  - #35 可在检查现有 Run 提交与持久化架构后，与 #32–#34 并行。
  - #36 与 #34（结果不确定）、#35（重复提交）协同。
  - #37 与 Runtime、Tool Gateway 相关项相互独立。
- **第三阶段 — #38 CI 质量门禁。** 可立即启动，但最终强制门禁必须纳入 #32–#37 引入的必要测试。

## 明确不做的（整体边界）

- **不替换 Policy 服务**，不引入新的身份提供方，不重新设计整个权限模型。
- **不构建企业级审批流程设计器**；确认机制只解决「服务端可控、可绑定、可审计」，不做可视化编排。
- **不承诺任意外部系统之间的恰好一次执行**；只承诺「不盲目重试、结果不确定时进入可对账状态」。
- **不为所有外部提供方实现专属对账集成**，也不构建通用分布式事务协调器。
- **不替换现有队列技术、向量库与 CI 提供方**；不重写整个测试套件。
- **不要求每个 PR Job 启动所有可选集成服务**，也不要求所有端到端测试在每次提交时执行。
- **不承诺特定检索质量分数**，除非先有评测数据集与测量方法。
- **不在本目录记录进度**，避免与 issue 形成两套状态。

## Review 指引

七项可独立评审、独立排期。建议按 #32 → 第二阶段并行 → #38 收口推进。评审重点：

- **#32 可信执行上下文**：`ExecutionContext` 是复用现有 policy 上下文对象还是新增；拒绝时的错误契约（结构化错误码）；上下文如何跨异步执行与 Worker 边界传递。
- **#33 服务端确认**：外部写操作的判定标准与风险分级由谁定义；参数规范化（canonicalization）方案——绑定的是原始参数还是规范化后的不可变表示；与既有 `pending_actions` 的关系。
- **#34 操作账本**：复用 runtime 任务表还是新建操作表；`unknown_outcome` 谁来触发对账（定时任务 / 人工）；与提供方幂等键的映射规则。
- **#35 Run 幂等**：幂等键由调用方提交还是服务端派生；与渠道层已有的消息去重（message-ID dedup）是否重叠、如何统一。
- **#36 生命周期与恢复**：取消是否要中断已分发的外部调用；Worker 租约机制是否已存在，不存在时的最小实现边界。
- **#37 知识验收**：能力声明的载体（文档 / 代码常量 / 配置）；异步索引场景下「可检索」的判定条件与轮询方式。
- **#38 CI 门禁**：现有 CI 是否已有会修改源文件的步骤（自动格式化修复）；哪些检查必须进 PR 门禁、哪些放定时任务。
